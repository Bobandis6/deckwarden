# P3.3 session prompt

Pull latest, then kick off P3.3 from deckwarden-build-plan.md — M3's third
package (~line 204): the Combo Radar panel — in-deck combos, one-card-away
with an add button, CI-legal only. Know what it is NOT before designing: the
Suggestions panel (P3.2) already surfaces one-away pieces as ranked
*candidates with evidence*; the Radar answers the other question — "what
does my deck already do, and what is it one card from doing" — organized by
COMBO, exhaustive within honest bounds, not re-ranked against staples. If
the two panels end up showing the same thing, one of them is wrong. The
architecture call to take FIRST and state: games/types.ts declares
`combos?: { findForDeck(cardIds, ciMask): Promise<ComboHit[]> }` — a stub
from before P2.5/P3.1 that nothing implements or consumes, and its IO-in-
the-adapter shape contradicts the "adapters declare, core translates" seam
P3.1 settled (combo tables are already game-agnostic: combo_pieces →
card_identities). Decide whether the capability keeps that shape or gets
the P3.1 treatment (core IO in src/lib/combos/, declarative adapter meta),
and evolve the anemic ComboHit contract to what the Radar actually renders:
results, templates, popularity, externalKey for the Spellbook deep link
(combo-list.tsx is the credit precedent — deep link per combo, walkthrough
deliberately not stored). The one-away SQL shape already exists in
recommend/queries.ts loadComboSignals (`having count(*) = pieceCount - 1`,
CI filter, COMBO_SCAN_LIMIT 200); in-deck is `= pieceCount` — one shared
query layer, never a second engine, and don't silently double the combo
scan cost per deck edit: say what the Radar route costs next to the
recommendations route it will sit beside. **The LATER.md row scoped to this
package fires now** — both halves, decisions not drift: (1) findForDeck
template semantics — a combo with template requirements ("a creature with
power 5+") is never "complete" on cards alone; in-deck detection must say
"also needs …" exactly as the engine's evidence phrasing does, never
promote it to done; (2) the Spellbook popularity floor — ingest keeps only
popularity ≥ 1 or NULL (the zero-popularity tail was 45k of 109k variants,
+38MB on the ~0.5GB Neon budget), so the Radar can only detect combos the
DB holds; lift it (one constant in spellbook-map.ts + re-ingest) or ship
over the kept set and re-record with reasoning and a new trigger. Unranked
(NULL-popularity) combos are real but unproven — the engine renders them
low-confidence; the Radar renders them honestly too, not hidden, not
inflated. Panel placement: read the P3.2 right-pane tab strip before
designing (Card | Suggestions — a third tab is the obvious slot, but decide
against what's there, including mobile stacking); reuse the P3.2 machinery
rather than re-deriving it — the commander gate (ciMask 0 = colorless-only
noise; same honest "add a commander" empty state; draft mode never fetches
a deck that doesn't exist), the settled-autosave refetch key
(src/lib/recommend/view.ts, test-enforced), and the add path (resolve
hydration with the id-mismatch guard → quiet add → autosave; no parallel
write path). If reuse means promoting panel helpers somewhere shared, do it
in this package rather than copy-pasting. New route follows house rules:
zod'd params, explicit caching intent (force-dynamic + no-store — mid-edit
deck state, token/session access), read access mirroring the deck GET, and
a rate-limit decision either way (precedent: RATE_LIMITS.recommendations
30/min per IP, enforced before deck access). Deployable outcome = the Radar
live in the prod builder showing at least one real in-deck combo and
one-away adds working, deployed and check-green, smoke coverage for the new
route (extend smoke:combos or add radar checks to smoke:recommend — the
Basalt Monolith + Rings of Brighthearth pair is the proven fixture: both in
deck → complete combo named; one in deck → one-away with the add target),
and the existing smokes still green against prod.
