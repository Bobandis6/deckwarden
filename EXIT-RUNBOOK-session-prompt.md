## What this package is NOT (scope fence)

- NOT a move. No DNS record changes, no Vercel setting changes, no domain removed from Vercel, no box unless the owner picked it at pre-flight, and the session never reads, copies or asks for a production secret: the runbook tells the owner how to carry them.
- NOT Postgres on the VPS. Neon stays (LATER row 96 keeps its own trigger); the runbook's database section is one connection string moving into Coolify's environment.
- NOT a CDN redesign. Row 279's choice (Cloudflare's proxy with a cache rule that reads origin headers, or the card page and the previews back on ISR where writes cost nothing) is written down as a recommendation with the measured cost of each, not implemented.

- NOT new workflow files: `src/lib/github-workflows.test.ts` pins full-SHA `uses:` lines and the `permissions:` block on everything under `.github/workflows`.
- NOT the README's hosting sentences (`README.md:22-24`, `:53-55` say Vercel hosts and deploys from `main`) or `next.config.ts:149-152`'s Vercel exception: the runbook lists them as the lines the move edits, with the wording.

## Facts you inherit

**What is already portable.**

- `output: process.env.VERCEL ? undefined : "standalone"` (`next.config.ts:152`; the comment above it records why Vercel's own packaging breaks on standalone), pinned at `src/lib/next-config.test.ts:54-57`. No `vercel.json` exists; the security headers and the enforcing CSP are set in `next.config.ts` (`SECURITY_HEADERS` `:39-45`, `contentSecurityPolicy()` `:100`) so "the VPS serves the same set from the same file" (`:23-24`). HSTS (`:44`, two years, `includeSubDomains`): Vercel sends a max-age of its own today; off Vercel ours is the only one, and `img.deckwarden.gg` is HTTPS already.
- No `@vercel/*` package (`package.json`); `next/og`'s ImageResponse is satori and runs anywhere (the five `opengraph-image.tsx` routes under `src/app/(site)/` and `src/lib/og/*`). The database client is plain postgres.js over TCP (`src/db/index.ts:1-3`); rate limiting is Postgres-backed because "per-instance memory dies on serverless" (`src/lib/rate-limit.ts:1-9`), which is also why it survives a move.
- The preview fonts are read by literal `join(process.cwd(), "assets/fonts/…")` (`src/lib/og/fonts.ts:38-39`) so output file tracing copies the two TTFs under `.next/standalone/assets/fonts/`. **The container's working directory must be the standalone root**, or `loadOgFonts` takes its catch (`:45`) and every unfurl silently repaints in the bundled Geist: no 500, so only a pixel or byte check catches it (below).
- Every nightly job runs from GitHub Actions against Neon and R2 (`.github/workflows/nightly-ingest.yml`: the six ingests, the mirror, the archive, the gauge, the purge, the backup, the prune, the ruleset and advisory watches, the keepalive), the restore drill too. Nothing in them knows the host. Migrations are the owner's `pnpm db:migrate` (`README.md:42`), also host-free. The runbook's "what does not move" section lists these with Neon, R2 and `img.deckwarden.gg`, Cloudflare DNS and the analytics beacon, Sentry, and the two OAuth apps.
- `/api/health` (`src/app/api/health/route.ts`): `force-dynamic`, one `select 1`, `{ ok: true, db: "up" }` 200 or 503 with a fixed message. It is the natural health-check target for Coolify, and each probe is one database statement: a 30-second interval is 2,880 statements a day against Neon's compute hours, so the runbook states the interval it recommends and the cost. (A static file such as `/icon-192.png` proves the process answers without a query; the runbook may propose that for liveness and `/api/health` for readiness, as a note, not a route.)

**What reads Vercel.**

- `src/lib/seo/site.ts:14-20` (`VERCEL_ENV` and `VERCEL_URL` for previews only; everything else, "local dev, VPS", defaults to `https://deckwarden.gg`), `src/lib/auth.ts:47-51` (`BETTER_AUTH_URL` → `NEXT_PUBLIC_SITE_URL` → `NODE_ENV`), `src/instrumentation.ts:22` and `src/instrumentation-client.ts:19` (Sentry's environment is `VERCEL_ENV ?? NODE_ENV`, "production" either way). The smokes: `scripts/sets-smoke.ts:321-336` reads `x-vercel-cache` and skips its cache checks when the header is null; `scripts/autofill-smoke.ts:368` and `:414` name Vercel only in a check's label. So every `pnpm smoke:*` runs unchanged against the container.
- CDN assumptions (LATER row 279): `/cards/:id` sends `CDN-Cache-Control: public, max-age=3600, stale-while-revalidate=86400` (`next.config.ts:17`, `:190`) and the card, hub and leader previews send `Cache-Control: public, s-maxage=86400, stale-while-revalidate=86400` (`src/lib/og/jpeg.ts:31`). Vercel's CDN honours both and strips the second before the browser sees it. Behind Traefik alone nothing caches: a card page renders on every request (~40 ms of CPU warm plus its database round trips, row 279), a preview is a satori render plus the JPEG encode, and the deck preview is already per-request and rate-limited (row 283). Row 280: ISR writes cost nothing off Vercel, and every deployment starts its own empty ISR cache there too. `/_next/image` (row 273): record what the container answers for `/_next/image?url=%2Ficon-192.png&w=48&q=75`; with `images.unoptimized` (`next.config.ts:163`) no page requests it, and a 400 is the right answer.
- Client IP: `clientIp` (`src/lib/decks/access.ts:55-62`) takes the first `x-forwarded-for` element, then `x-real-ip`. Vercel writes that header itself. Behind Traefik the header is whatever Traefik's forwarded-headers settings make it; behind Cloudflare's proxy a client's own `x-forwarded-for` can survive ahead of the real address unless the edge or Traefik is told to trust only its own appended value, where `CF-Connecting-IP` is the trustworthy one. `decks.created_ip`, the purge policy and every per-IP limiter read `clientIp`, so the runbook must say, for the chain it recommends, which header is trustworthy and what to set so that it is (verify against the current Traefik and Cloudflare docs; cite them).
- The pool: `max: 1` (`src/db/index.ts:27`), sized for "one connection per function instance". One long-lived process on a VPS serialises every query of every concurrent request through that one connection. Measure it (the checks below). If the concurrent run shows queuing, the change is a pool size read from the environment with 1 as the default (Vercel unchanged), its test beside `createDb`'s, and the runbook names the variable; if not, a LATER row with the measured numbers and the trigger "p95 climbs on the VPS". This is the one code change the package may carry, and only if measured.
- Build-time needs: `next build` prerenders the ISR pages (`/sets`, `/precons`, `/brackets`, the hubs' and leaders' first paths) against `DATABASE_URL`, loads `src/lib/auth.ts` (`BETTER_AUTH_SECRET`, row 270) and inlines the `NEXT_PUBLIC_*` values (the CSP's Sentry origin from `NEXT_PUBLIC_SENTRY_DSN`, `next.config.ts:102-104`; `NEXT_PUBLIC_TCGPLAYER_PARTNER_BASE` pinned to `""`, `:170`). So the image build needs the runtime environment and network to Neon; the rehearsal build needs the `dev` branch's string, passed as a BuildKit secret, never an `ARG` or `ENV` (both land in the image's layers and history).
- The environment inventory is `.env.example`, complete by construction (S8 made `grep process.env` and the file agree). Production values live in Vercel's Production environment and nowhere else; the runbook tells the owner to carry them into Coolify by hand, or through `vercel env pull --environment=production` into a file that is deleted the same hour, never through the repo, the chat or a session.
- Analytics (row 313, `src/app/layout.tsx:120-121`): the beacon is in the page because the DNS records are DNS-only. If the hostname is ever proxied (orange cloud), Cloudflare's automatic injection must stay off or every page view counts twice; the runbook says so next to the row 279 choice.
