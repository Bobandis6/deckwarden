# P3.4 session prompt

Pull latest, then kick off P3.4 from deckwarden-build-plan.md — M3's fourth
package (~line 205): Cut Coach — over-limit ranking with explicit tradeoff
text. Know what it is NOT before designing: Suggestions (P3.2) ranks
OUTSIDE cards to add against global signals; the Coach ranks the deck's OWN
cards for removal when the deck exceeds its legal size, and its product is
the TRADEOFF TEXT — what cutting this card costs the deck, in the deck's
own terms — never a bare ordered list (M3's exit line: "every suggestion
shows its evidence"). It is also not an auto-trimmer: one click per cut,
user-driven, through the editor's own remove/setQty path (decide the
qty > 1 semantics — decrement vs remove — and state it), never a parallel
write path, and never the leader zone. The feature plan's §Cut Coach
(deck-building-website-feature-plan.md ~line 189) lists seven ranking
inputs; ship the honest subset that has real data behind it — popularity
(edhrec_rank: a rank-40k card is more cuttable than a staple, phrased with
the same scoped tier words as recommend.ts), curve-bucket overload vs
MTG_CURVE_TEMPLATE (via recommend.curve.bucketOf), role overload vs
adapter.hub.roles via user tags, complete-combo membership, and price
(cheapestUsd is client-held) if it earns its place — "low synergy" and
"weak performance in comparable decks" have no corpus (cold-start rule: a
missing signal is missing, never a faked synergy score). The architecture
call to take FIRST and state: where does the ranking run? The client
already holds everything per-card — EditorCard is full CardData
(popularity, cheapestUsd, costValue, primaryType), tags live on entries,
and both templates are adapter declarations — so the validate/analyze
precedent (pure client logic, instant mid-edit feedback, zero Neon cost,
no rate limit, works even while autosave is dirty) competes with the
recommendations-route precedent. The ONE signal the client lacks is combo
membership — and GET /api/decks/[id]/combos (P3.3) already returns exactly
that under the same panel fetch policy: if the ranker is pure, say how it
gets combo data (reuse that route's response — never a second combo query
path) and what it renders while that fetch is pending or absent (honest
degradation, not silence); if you add a route instead, justify its cost
next to the two read routes already there and follow house rules (zod'd
params, explicit caching intent, read access mirroring the deck GET, a
rate-limit decision with the 30/min precedent). Either way the seam is
P3.1's: the machine (weights, evidence assembly, confidence, ordering) is
core and game-ignorant like rank.ts; MTG declares only phrasing and the
templates it already declares — decide whether that extends RecommendMeta
or stands alone, and reuse the RecommendationEvidence shape (source, why,
with, howOften, confidence) rather than inventing a second evidence
contract. A card in a COMPLETE in-deck combo is the tradeoff that matters
most: "part of Basalt Monolith + Rings of Brighthearth — cutting it breaks
the combo" rendered explicitly (and ranked accordingly), never a piece
silently listed as an ordinary cut; template-combo honesty carries over —
deckComboStatus (P3.3, test-enforced) says a template combo was never
"complete" to begin with. **The LATER.md row scoped to this package fires
now** — its trigger names P3.4 alone; both halves, decisions not drift:

matching semantics, e.g. case), counting ONLY tagged cards and saying so —
