## Corrections to the contract (found while writing this prompt — read before the pin matrix)

Checked against the code and the installed Better Auth 1.7.2 at `879db10` (paths under `node_modules/better-auth/dist/` are written `BA/`; `@better-auth/core`'s dist, under `node_modules/.pnpm/@better-auth+core@1.7.2*/node_modules/@better-auth/core/dist/`, is `CORE/`).

1. **Better Auth's refresh switch rewrites more than the picture.** `overrideUserInfoOnSignIn` (per provider; `CORE/oauth2/oauth-provider.d.mts` ~358, default false) is read on the redirect callback only (`BA/api/routes/callback.mjs` ~232). With it, a returning sign-in calls `updateUser(id, { name, image, ...mapped fields, email, emailVerified })` (`BA/oauth2/link-account.mjs` 183–192). `mapProfileToUser` cannot drop the name or the email — the callback forces `name` to a string and requires an email. So D5's "the refresh changes the picture only" needs a narrowing mechanism, and one exists: `databaseHooks.user.update.before` — `BA/db/with-hooks.mjs` 43–58 merges a hook's `{ data }` over the update (and `false` skips it), and the adapter factory skips `undefined` keys on an update (`CORE/db/adapter/factory.mjs` ~113). A hook that sets `name`, `email` and `emailVerified` to `undefined` on the callback path leaves the picture alone in the write. Step 1 proves it, and what `ctx.path` reads there (expected `/callback/:id` — `nextCookies` matches the same way, `BA/integrations/next-js.mjs` ~41). `account.accountLinking.updateUserInfoOnLink` is not the tool: it fires only when a new provider is linked.
2. **The email collision is answered, not open** (WAVE3 B called it unverified). The override's write is not caught (`link-account.mjs` 186 → `BA/db/internal-adapter.mjs` ~599–610; `callback.mjs` ~241–244 rethrows), and `users.email` is UNIQUE (`src/db/schema.ts` 271): a provider email equal to another user's makes the sign-in throw. Narrowing the write removes the email from it, and with it the collision. Without the override, a returning sign-in writes only `emailVerified` and the account's tokens (`link-account.mjs` 153–181) — which is why `users.image` has been frozen since sign-up.
3. **"Verify first against Better Auth's in-memory adapter": the harness exists.** `src/lib/auth/callback-url.test.ts` drives a full Discord round trip on the memory adapter with a stubbed fetch ("ends on the callback byte for byte, with a session", from 103); its `advanced.disableOriginCheck: false` (docblock 9–14) is load-bearing. A second round trip with a changed picture, name and email extends it. (`better-auth/test`'s `getTestInstance` runs node:sqlite with email/password — not this.)
4. **"The card box is X2's island" — the island cannot pick.** `NameSuggest` (`src/components/search/name-suggest.tsx`) requires `rowHref` (83), drops rows without an href (161) and renders every row as a `Link` (235); only its footer row takes a click (~306–333). X5 needs a pick mode (a callback in place of `rowHref`, on the footer's pattern) or its own small island on `ui/autocomplete`. Decide; X2's pins (`name-suggest` tests, the hub filters, `/cards`' Name box) stay green either way.
5. **A suggest row carries no printing.** `GET /api/cards/suggest` answers `{ id, name, slug, isLeader, typeLine, colorsMask, ciMask, externalKey, image }` — the printing id is selected and stripped (`src/lib/search/suggest.ts` ~91, 138–147), `image` is the default printing's small full-card image, the row shape is pinned by `toEqual` (`src/app/api/cards/suggest/route.test.ts` 116–129), and the edge keeps copies an hour plus a day stale. Leave the suggest response alone: the PUT takes the card id and resolves the default printing itself. `loadDefaultPrinting` (`src/lib/hub/queries.ts` ~64–71) does NOT filter removed printings — the route must.
6. **One null, two meanings.** `fetchScryfallArtMeta` (`src/lib/cards/art.ts` 69–85) returns the same `null` for "no crop or no artist" and for "Scryfall answered non-OK or the fetch threw". E promises a refusal sentence for a printing with no resolvable artist AND "Scryfall unreachable at Save: the choice is refused, the current picture stays". Widen the result (a reason) without changing what its callers do today (the OG images, the hub banners, `GET /api/cards/[id]/art`, the editor's ambient art), or word one sentence for both. Decide and pin.
7. **"The URL is derived from the printing id" vs `art.ts`' rule.** `art.ts`' docblock (8–16) says art's source is the Scryfall API by printing id, never a derived CDN URL, because the artist lives only there. X5 stores the artist at Save (from the API), so rendering can derive the crop — `scryfallImageUrl(printingId, "art_crop", "front")` (`src/lib/cards/images.ts` 19–26) — and the header, a client island on every page, can only derive. Reconcile it in writing (that docblock and REDESIGN's X5 section), and prove the derived URL is the API's `image_uris.art_crop` path (minus its `?` stamp) for a normal card and a double-faced one. `printingImageUrl`'s override (33–42) is for full-card images and never applies to art.
8. **24 px is not a `UserAvatar` size.** `UserAvatar` takes `48 | 64` (`src/components/profile/user-avatar.tsx` 20–23) and its test pins the two page sizes (~89–99); the header's own 24 px `Avatar size="sm"` (`src/components/auth/account-slot.tsx` 112–116) still uses `charAt(0)` (101). Row 110 fires by adding a 24 size (`size-6`, a small fallback) and moving the header onto it; the first-code-point rule then covers all three sites.
9. **"Discord picture" needs a rule for two providers.** A refresh writes the picture of whichever provider signed in last, so a user linked to both Discord and Google gets the last one. `/account` already lists the linked providers (`src/app/(site)/account/page.tsx` 150–153, 200–202). Decide how the dialog names the first choice — the provider of the latest sign-in, or provider-neutral words ("Your sign-in picture") when both are linked.
10. **The cookie cache and the refetch.** The session cookie cache carries additional fields for up to 300 s (`src/lib/auth.ts` 63–68; `BA/cookies/index.mjs` ~76–79). After Save the header must call `useSession().refetch({ query: { disableCookieCache: true } })` — typed (`BA/client/react/index.d.mts` 31–33) and it updates the shared session atom; `authClient.getSession()` does not update the atom, and `$sessionSignal` refetches through the stale cache. Never add `disableRefresh`: it stops the cookie's re-issue (`BA/cookies/session-store.mjs` 163–170 defines both flags; `BA/api/routes/session.mjs` ~48 skips the cache). Alternatively the PUT itself calls `auth.api.getSession({ headers, query: { disableCookieCache: true } })` and `nextCookies` sets the fresh cookie on the Save response (`BA/integrations/next-js.mjs` ~72–99). `/account`'s server render reads the cookie cache too (`account/page.tsx` 113): read the choice from the `users` row there — the page already does so for `username` (154–160) — or `router.refresh()` only after the cookie is re-issued.
11. **The additional fields.** `input: false` fields are refused by `/update-user` when truthy (moot — it is closed) and skipped from a provider profile (`BA/db/schema.mjs` 59–77, 116–127); they reach `getSession` and `useSession` unless `returned: false`. Declare `required: false` explicitly — the type documents `true` as the default. Type `"json"` exists, and the Drizzle adapter on Postgres supports JSON. Write the choice through Drizzle, never `auth.api.updateUser` (it would refuse the field). `inferAdditionalFields` adds client types only; there is no runtime client change.
12. **A limiter of its own.** `profileWrite` (`src/lib/rate-limit.ts` 112–118, 10 an hour per user) guards username changes; sharing it would let picture saves spend them. Add an avatar limiter, in the order `PATCH /api/profile` uses (session → limiter → JSON → zod → work; `src/app/api/profile/route.ts` 34–78).
13. **"Refresh now" is a `/sign-in/social` round trip**: Better Auth limits sign-ins to 3 per 10 s per IP; each use creates a session row (the old one lives to its 7-day expiry); Discord's default `prompt: "none"` makes it a click-through. Name these in the risks; no token route reopens (row 108).
14. **The privacy page names what is stored**: "display name, email address, and avatar URL" (`src/app/(site)/privacy/page.tsx` 35) and the profile's "avatar" (40). X5 stores a picture choice — a card's printing id, its name and its artist — so the copy changes in this package: it is a promise to users.
15. **WAVE3's X1-era citations have drifted** (not X5's; noted so nobody trusts them): §B's `account-slot.tsx` 58–60, 96 and 43–48 are now Sign in 83–85, the name row 122–130 and the menu links 46–51; §G's `account/page.tsx` 101–112 is now 119–131.
