## Design decisions to make explicitly (disclose + test-pin each)

1. Block set + frozen ids. Suggested mapping of the bullet: `don-curve` histogram over cost 1–10 (last bucket "7+"? decide vs OP's real distribution — MTG's convention is index=cost, last bucket N+), `counters` — 1K count, 2K count, no-counter count, and whether "counter totals" also means the summed counter value (a stat like "+41,000 total"); `blockers` stat, `trigger-density` stat (count of trigger cards, qty-weighted, and/or per-50 %), `categories` breakdown (character/event/stage), `searchers` table (card · looks N · live targets in THIS deck · hit %). Freeze ids in one place; the renderer is generic so ids only matter for tests and future references.
2. Searcher hit-rate model: hypergeometric P(≥1 target in top N). Decide the population honestly — the resolved deck at game time isn't the full 50 (the searcher itself is on the field, cards are drawn) — the defensible simple model is "fresh 50-card deck minus one copy of the searcher", disclosed in the block title/hint. Pin 2–3 hand-computed values in tests.
3. Qty weighting everywhere (4x a Blocker = 4), matching mtg/analyze.ts.
4. Mid-build honesty: blocks compute over whatever is in the deck (9/50 cards → real numbers over 9), no projected denominators; empty deck → empty-but-rendered vs no blocks (check what MTG does at 0 cards and match).
5. Attributes (Strike/Slash/…) breakdown: the plan bullet does NOT name it — leave it out (scope fence) unless it falls out free AND you disclose it as an extra.
